# Локальний пілот історії сповіщень

Задача 01 проходить шлях від валідного графіка до серверного запису, API та картки на телефоні. Хмарного акаунта й push credentials для цього етапу не потрібно. Node-сервер є локальним тестовим транспортом; Cloudflare/D1 та реальна доставка перевіряються окремо в задачі 02.

## Запуск

Потрібні Node.js 24 та встановлені залежності проєкту.

1. Запустити `pnpm notifications:local` з кореня репозиторію. Сервер слухає тільки `127.0.0.1:8787`, SQLite зберігається в ігнорованому каталозі `.expo/notifications/`.
2. Для Android USB виконати `adb reverse tcp:8787 tcp:8787`.
3. Запустити Metro зі значенням `EXPO_PUBLIC_NOTIFICATIONS_API_URL=http://127.0.0.1:8787`. Для ізольованого запуску можна використати чинний `start:e2e`; основне сховище локацій тоді не змінюється. Нова native-збірка потрібна для доданого SecureStore.
4. Обрати чергу на головному екрані. Bootstrap реєструє інсталяцію без запиту дозволу ОС; дозвіл і реальний push додаються в задачі 02.
5. Відкрити «Сповіщення» й завантажити порожню історію. Лише після реєстрації виконати `pnpm notifications:fixture`.
6. Оновити історію жестом. З’явиться одна картка «Опубліковано графік» на дату захопленого графіка 10 жовтня 2026 року. Повторний запуск команди не дублює картку.

Fixture запускається окремою локальною CLI-командою; у HTTP API немає маршруту вставки подій. Production-клієнт не має автоматичного localhost або фіктивного fallback. Локальна команда не є сервісом опитування поточного графіка.

## Контракт

- `POST /v1/installations`: тіло містить випадкові `id` та `secret`; відповідь — `id` і серверний `startedAt`. Секрет зберігається на сервері як SHA-256; повторний запит повертає ту саму інсталяцію.
- `GET /v1/history`: заголовки `X-Installation-Id` та `Authorization: Bearer …`. Відповідь — `items` і `nextCursor`; курсор передається параметром `cursor`, сторінка містить до 50 записів. Справжні секрети не записувати в журнали.
- `GET /health`: локальна перевірка доступності.
- Відповіді мають `Cache-Control: no-store`. Невідомі маршрути повертають 404; некоректні запити — 400; неправильний секрет — 401; помилка сховища — 503.

Початок історії фіксується також послідовністю подій: однакові timestamps та повторна обробка старої публікації не додають її новій інсталяції. Публікація та одержувачі записуються однією транзакцією. SQLite зберігає дані між запусками; майбутній D1-адаптер використовує той самий асинхронний контракт бази.

На пристрої тільки ID зберігається в MMKV; секрет — у SecureStore. Відсутність локального ID означає нову інсталяцію, навіть якщо iOS залишила старий Keychain-секрет. Ізольований E2E використовує окремий ключ секрету.

## Перевірки

- `pnpm notifications:test`: Node integration tests із реальною SQLite, захопленим HTML, API та мобільним клієнтом: дублікати, початок історії, доступ, перезапуск, валідація та пагінація.
- `pnpm test --runInBand src/features/svitlo/notifications`: Jest перевірки створення інсталяції та видимих станів історії.
- `pnpm type-check` та `pnpm lint`: загальні перевірки мобільного й серверного TypeScript.

Зберігання 30 днів, офлайн-кеш, прочитаність, інші типи сповіщень та переходи до датованого графіка розширюються наступними задачами. Завдання 01 не підтверджує безкоштовні квоти хмари або працездатність push.
