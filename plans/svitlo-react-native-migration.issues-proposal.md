# Пропозиція issues: перенесення Svitlo на React Native

Статус: поділ, залежності та типи задач погоджені користувачем; окремі issue-файли створено. Актуальний перелік: [індекс задач](./svitlo-react-native-migration/README.md).
Джерело: [PRD](./svitlo-react-native-migration.prd.md).

Кожен погоджений пункт збережено окремим файлом у каталозі `plans/svitlo-react-native-migration` з указаним нижче ім’ям. Це локальні задачі реалізації, не опубліковані GitHub issues.

AFK означає, що задача не потребує нових продуктових рішень. HITL означає, що вказану зміну поведінки або результат платформної перевірки потрібно переглянути з власником продукту. Нові помилки, виявлені в будь-якій задачі, повідомляються окремо за правилом PRD.

Кожна задача завершує сценарій від отримання або збереження даних до видимого результату. Модулі нарощуються в цих задачах; окремих задач «написати весь API», «написати всі моделі» або «зробити весь UI» немає.

## 01. Перший запуск, вибір черги та реальний поточний стан

Майбутній файл: `01-first-launch-and-live-status.issue.md`.
Тип: AFK. User stories: 1–6, 12–14, 20, 25–26, 28.

### What to build

Користувач відкриває застосунок, бачить пропозицію обрати чергу, отримує список черг Полтаваобленерго, вибирає свою та переходить до головного екрана з локацією «Дім» і поточним станом. Вибір зберігається після перезапуску.

У цьому сценарії замінити стартові маршрути Obytes на навігацію Svitlo з головною вкладкою, вкладкою черг та порожньою вкладкою сповіщень. Вкладка черг до задачі 06 ще не надає загальної таблиці. Не показувати демонстраційний вхід, feed або onboarding. Налаштувати окрему локальну ідентичність застосунку для платформ; прив’язка до EAS-акаунта та публікація не є частиною задачі.

Запит і HTML-парсер сховати за адаптером оператора, вибір і збереження — за сховищем локацій, поточний стан — за незалежною від React моделлю графіка. Отримати фактичний приклад відповіді й задокументувати її контракт. Таймер і часова шкала додаються в задачі 04.

### Acceptance criteria

- [ ] При чистому запуску немає локацій та обраної черги; є текст «Оберіть свою чергу, щоб побачити графік відключень» і дія вибору.
- [ ] До вибору черги немає персонального статусу та таймера.
- [ ] Доступні черги отримуються з нормалізованої відповіді оператора; не підставляється черга 3.1 або демонстраційний графік.
- [ ] Вибір створює активну локацію «Дім» з іконкою дому та правильною чергою, яка відновлюється після перезапуску.
- [ ] Картка розрізняє «є світло», «немає світла», «можливе відключення» та «немає даних»; невідомий тип не стає наявністю світла.
- [ ] Завантаження, помилка запиту та відсутність черги у відповіді мають окремі зрозумілі стани.
- [ ] Парсер враховує rowspan, півгодинні клітинки, `24:00` і об’єднує лише суміжні однакові типи.
- [ ] Збережено українські тексти, базове компонування, кольори та нижню навігацію за Kotlin-кодом; вкладка сповіщень порожня.
- [ ] Налаштована окрема ідентичність збірки; шаблонний EAS-проєкт Obytes не використовується як проєкт Svitlo.
- [ ] Парсер і поточний стан перевірені на контрольованих фікстурах; новий код проходить TypeScript і ESLint. Додатковий компонентний тест першого вибору — пропозиція з PRD, що потребує підтвердження обсягу тестів.

### Blocked by

None — можна починати відразу після погодження поділу.

## 02. Додавання, редагування й перемикання локацій

Майбутній файл: `02-manage-and-switch-locations.issue.md`.
Тип: AFK. User stories: 7–9, 12–14, 25, 28.

### What to build

Користувач додає другу локацію, вибирає її назву, чергу й іконку, перемикається між локаціями та редагує їх. Головний екран показує стан активної локації, а зміни відновлюються після перезапуску. Селектор і діалог відтворюють Kotlin-компоненти.

### Acceptance criteria

- [ ] Доступне додавання локації з назвою, чергою зі списку оператора та іконками, представленими в Kotlin-коді.
- [ ] Нова локація стає активною, як у Kotlin, і показує власний графік.
- [ ] Редагування активної локації оновлює її відображення та стан; зміна черги не залишає графік попередньої черги.
- [ ] Перемикання локації не повторює запит без потреби, коли графіки потрібної дати вже завантажені.
- [ ] Перелік локацій зберігається після перезапуску; поведінку збереження активного вибору явно описано як технічне уточнення PRD.
- [ ] Незавершений запит попереднього вибору не перезаписує стан поточної локації.
- [ ] Селектор та діалоги відповідають Kotlin-коду й придатні для роботи з клавіатурою на обох платформах.
- [ ] Поведінка операцій зі сховищем перевірена unit-тестами; TypeScript і ESLint проходять.

### Blocked by

- Задача 01 — `01-first-launch-and-live-status.issue.md`.

## 03. Видалення локацій і повернення до вибору черги

Майбутній файл: `03-delete-locations-and-reset-selection.issue.md`.
Тип: AFK. User stories: 10–12, 25, 28.

### What to build

Користувач видаляє локацію через наявний сценарій редагування. Видалення активної локації переводить його на одну з решти, а видалення останньої повертає до явної пропозиції вибрати чергу. Дані не відновлюються помилково після перезапуску.

### Acceptance criteria

- [ ] Видалення неактивної локації не змінює поточний графік.
- [ ] Після видалення активної локації за наявності інших вибирається перша з решти, відповідно до Kotlin-поведінки.
- [ ] Останню локацію можна видалити; активний вибір очищується, персональні статус і таймер зникають.
- [ ] Порожній стан містить явний заклик обрати чергу; повторний вибір знову створює «Дім».
- [ ] Видалення збережене між запусками й не скасовується пізнім результатом запиту.
- [ ] Unit-тести покривають видалення неактивної, активної та останньої локації; TypeScript і ESLint проходять.

### Blocked by

- Задача 02 — `02-manage-and-switch-locations.issue.md`.

## 04. Часова шкала та відлік до наступної події

Майбутній файл: `04-timeline-and-next-event-countdown.issue.md`.
Тип: HITL. User stories: 13–14, 16–18, 25, 27–28.

### What to build

На головному екрані вибраної локації показати поточні та майбутні інтервали, поточний стан, наступну відому подію й відлік до неї. Відтворити часову шкалу та картку Kotlin за кодом, зберігаючи всі типи станів.

Пояснити власнику продукту помилки оригіналу: ознака поточного інтервалу обчислюється лише при зміні графіка, а таймер може зберігати старе значення, якщо наступної події немає. Погодити виправлення і трактування переходу до можливого відключення, перш ніж завершувати цю поведінку. Рекомендація: відлік до найближчої відомої зміни стану із текстом, який не називає можливе відключення гарантованим.

### Acceptance criteria

- [ ] Виправлення часової логіки та тексти переходів для можливого відключення погоджені й зафіксовані.
- [ ] Часова шкала розрізняє чотири типи, не зливає можливе відключення або невідомий стан зі світлом.
- [ ] Відображаються поточні та майбутні інтервали; поточний інтервал оновлюється з плином часу.
- [ ] Таймер використовує поточний час і визначену наступну подію, не стає від’ємним і не зберігає попередню подію після зміни локації.
- [ ] За відсутності наступної події або даних немає вигаданого відліку.
- [ ] `24:00` є кінцем доби, без штучної втрати останньої хвилини.
- [ ] Розрахунки ізольовані від React; unit-тести перевіряють межі інтервалів, півгодинні переходи, різні типи та відсутність події з контрольованим часом.
- [ ] Компонування шкали й таймера відповідає Kotlin-коду; TypeScript і ESLint проходять.

### Blocked by

- Задача 01 — `01-first-launch-and-live-status.issue.md`.

## 05. Підтверджений стан без запланованих відключень

Майбутній файл: `05-no-outages-planned-state.issue.md`.
Тип: AFK. User stories: 14–16, 20, 28.

### What to build

Користувач бачить «Відключення не заплановані на сьогодні», коли оператор явно підтверджує це для вибраної черги або повертає повний графік дня лише зі світлом. Розпізнавання проходить від відповіді оператора через нормалізовану модель до головного екрана.

Отримати та перевірити фактичний формат явного повідомлення. Якщо його зразок недоступний, документувати це обмеження: не вигадувати маркер і не стверджувати, що ця гілка перевірена. Підтвердження для всіх черг можна застосовувати до вибраної лише коли це випливає зі змісту відповіді.

### Acceptance criteria

- [ ] Повний день зі станом «є світло» дає погоджений текст для вибраної черги.
- [ ] Явна відповідь оператора розпізнається за перевіреним контрактом, з урахуванням дати й області її дії.
- [ ] Якщо явна відповідь не містить переліку черг, наявний вибір локації не втрачається; поведінка першого вибору не використовує вигадані доступні черги.
- [ ] Порожня відповідь, неповний день, невідома клітинка, відсутня черга та помилка запиту не стають станом без запланованих відключень.
- [ ] Картка не показує відлік до вигаданого відключення; модель надає результат, який задача 04 може використати без окремого парсингу в UI.
- [ ] Unit-тести покривають позитивні й негативні умови на перевірених фікстурах; неперевірені формати явно зазначені.
- [ ] TypeScript і ESLint проходять.

### Blocked by

- Задача 01 — `01-first-launch-and-live-status.issue.md`.

## 06. Загальна таблиця всіх черг

Майбутній файл: `06-global-schedule-matrix.issue.md`.
Тип: AFK. User stories: 14, 20–21, 25, 28.

### What to build

Користувач переходить на вкладку черг і бачить загальну таблицю Полтаваобленерго з виділенням своєї активної черги. Таблиця використовує ту саму нормалізовану відповідь, що й головний екран, і відтворює компонування Kotlin.

### Acceptance criteria

- [ ] Показані черги, підчерги, часова сітка й легенда відповідно до фактично використовуваного Kotlin-компонента.
- [ ] Є світло, відключення, можливе відключення та невідомий стан відображаються послідовно з головним екраном.
- [ ] Активна черга виділена; якщо локація не вибрана, таблиця доступна без помилкового виділення.
- [ ] Зміна активної локації оновлює виділення без окремого HTML-парсингу або дубльованого запиту.
- [ ] Завантаження, відсутні дані й помилка мають зрозуміле відображення.
- [ ] Таблиця придатна для прокручування на телефонах Android та iOS.
- [ ] Якщо відтворюється статистика Kotlin-таблиці, вона використовує фактичну тривалість інтервалів; нові розбіжності погоджуються за правилом PRD.
- [ ] Перетворення інтервалів у клітинки перевірене unit-тестами; TypeScript і ESLint проходять.

## 07. Ручне оновлення та відновлення після помилки

Майбутній файл: `07-refresh-and-error-recovery.issue.md`.
Тип: AFK. User stories: 19–20, 28.

### What to build

Користувач оновлює графік жестом потягування й бачить результат запиту. Після невдалого запиту він може повторити спробу, а успішний результат прибирає помилку та синхронізує всі екрани, що використовують цей графік.

### Acceptance criteria

- [ ] Pull-to-refresh головного екрана виконує новий запит для поточної дати, навіть якщо графік уже є в пам’яті.
- [ ] Індикатор завершується після успіху та після помилки; повторні дії не створюють неконтрольованих паралельних запитів.
- [ ] Останні коректні дані не знищуються перед отриманням заміни; помилка оновлення відрізняється від початкової відсутності даних.
- [ ] Після успішного повтору попередня помилка очищується й видимі дані оновлюються.
- [ ] Якщо загальна таблиця вже реалізована, вона бачить той самий оновлений графік без другого джерела стану.
- [ ] Unit-тести перевіряють результати успіху та помилки; інтеграційний тест повторного запиту є запропонованим додатковим покриттям PRD.
- [ ] TypeScript і ESLint проходять.

### Blocked by

- Задача 01 — `01-first-launch-and-live-status.issue.md`.

## 08. Збережений графік без інтернету

Майбутній файл: `08-offline-schedule-and-freshness.issue.md`.
Тип: AFK. User stories: 12–16, 20, 22–24, 28.

### What to build

Після успішного отримання графік зберігається локально з датою та часом оновлення. Користувач повторно відкриває застосунок без інтернету і бачить збережені дані з позначкою. Прострочений графік не керує сьогоднішнім статусом або таймером.

### Acceptance criteria

- [ ] Успішна нормалізована відповідь, включно з підтвердженим станом без відключень, зберігається з датою графіка та часом отримання.
- [ ] Після перезапуску й невдалого запиту доступний останній збережений графік та список локацій.
- [ ] Позначка кешу, помилка оновлення та час останнього успіху не створюють враження щойно отриманих даних; мережеву помилку не називати відсутністю інтернету без підстав.
- [ ] Поточний збережений графік дозволяє користуватися погодженими статусами та шкалою з позначкою актуальності.
- [ ] Дані попереднього дня позначені як попередні й не визначають сьогоднішні статус, відлік або повідомлення про відсутність запланованих відключень.
- [ ] За відсутності, пошкодженні або несумісності кешу застосунок не падає та не підставляє графік.
- [ ] Відновлення зв’язку та успішне ручне оновлення замінюють кеш і очищують попередню помилку.
- [ ] Unit-тести перевіряють відновлення та прострочення; інтеграційні тести запису, перезапуску й помилок сховища є запропонованим додатковим покриттям PRD.
- [ ] TypeScript і ESLint проходять.

### Blocked by

- Задача 04 — `04-timeline-and-next-event-countdown.issue.md`.
- Задача 05 — `05-no-outages-planned-state.issue.md`.

## 09. Актуальність після опівночі та повернення в застосунок

Майбутній файл: `09-day-rollover-and-app-resume.issue.md`.
Тип: HITL. User stories: 13, 16–18, 23–24, 27–28.

### What to build

Користувач залишає застосунок відкритим до наступного дня або повертається після перерви. Екрани перевіряють актуальну дату, переобчислюють стан і таймер та отримують новий графік за потреби. Дані вчорашнього дня не видаються за сьогоднішні.

Погодити запропоновані в PRD технічні уточнення: часовий пояс `Europe/Kyiv` незалежно від налаштування пристрою та перевірку дати при опівночі й поверненні у foreground. Це не фонова періодична робота й не механізм сповіщень.

### Acceptance criteria

- [ ] Часовий пояс і поведінка опівночі/foreground погоджені та задокументовані.
- [ ] Формат дати запиту та розрахунки стану використовують спільне правило часу, включно з пристроєм в іншому часовому поясі.
- [ ] Після зміни дати попередній графік відразу втрачає право визначати поточний стан і таймер.
- [ ] Новий графік завантажується без потреби перемикати локацію або перезапускати застосунок.
- [ ] Після повернення у foreground відлік відновлюється за поточним часом, а не за кількістю пропущених tick-подій.
- [ ] За невдалого запиту нового дня збережені попередні дані залишаються явно позначеними.
- [ ] Unit-тести охоплюють опівніч, зміну часового поясу пристрою та відсутність даних нового дня; сценарій повернення перевірений на платформі або компонентним тестом у погодженому обсязі.
- [ ] TypeScript і ESLint проходять.

## 10. Приймання перенесеної версії на Android та iOS

Майбутній файл: `10-android-ios-migration-acceptance.issue.md`.
Тип: HITL. User stories: 1–28, в межах першого етапу PRD.

### What to build

Завершити перенесення перевіркою всіх погоджених сценаріїв на Android та iOS, усунути виявлені платформні проблеми й підготувати короткий звіт про виконання критеріїв PRD. Порівняння вигляду виконується за Kotlin-кодом; редизайн не проводиться.

Це наскрізне приймання застосунку, а не відкладене написання тестів для всіх попередніх задач. Кожна попередня задача вже має власну перевірку. Людська участь потрібна для перегляду результату та забезпечення платформного середовища, якщо його немає.

### Acceptance criteria

- [ ] Є перевірені запуск і основні сценарії на Android та iOS; відсутнє середовище позначається як блокер, а не як успішна перевірка.
- [ ] Android-версія встановлюється поряд із Kotlin-версією без заміни її даних.
- [ ] Пройдені перший вибір, CRUD локацій, видалення останньої, статуси, таймер, таблиця, ручне оновлення та повторний запуск без інтернету.
- [ ] Діалоги, клавіатура, safe area, системна кнопка назад Android та прокручування таблиці не блокують користування.
- [ ] Вкладка сповіщень порожня; відсутні шаблонні продуктові екрани, віджети й фонові сповіщення.
- [ ] Перевірено вигляд за реально використовуваним Kotlin-кодом; не заявляється піксельна відповідність без перевірки оригіналу.
- [ ] Поточний API-контракт перевірений; обмеження щодо зразка явної відповіді без відключень, якщо залишилися, зазначені у звіті та не приховані.
- [ ] TypeScript, ESLint та погоджені тести проходять; додаткові інтеграційні, компонентні та автоматизовані E2E не вважаються погодженими без рішення щодо тестового обсягу.
- [ ] Видимі зміни поведінки й виправлення переглянуті власником продукту; підготовлено результат для початку окремого редизайну.
- [ ] Збірки не прив’язані до шаблонного EAS-проєкту Obytes; якщо потрібен EAS, реальна прив’язка погоджена. Публікація в магазинах не виконується.
