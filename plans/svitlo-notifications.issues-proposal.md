# Пропозиція issues: сповіщення та історія Svitlo

Дата: 11 жовтня 2026 року.

Статус: PRD, модулі, обсяг тестування й розбиття на 15 задач погоджені 11 жовтня 2026 року. Окремі issue-файли створено; [індекс і поточні статуси](./svitlo-notifications/README.md).

Джерело: [PRD](./svitlo-notifications.prd.md).

AFK — реалізація за погодженими вимогами без нових продуктових рішень. HITL — потрібні зовнішні доступи або фактичне приймання на платформах; причину вказано в задачі. Усі реалізаційні задачі дають перевірюваний наскрізний результат і включають свої тести. Фінальна задача є окремим етапом приймання пілота.

Перша задача локально перевіряє вертикаль без хмарних доступів. Друга перевіряє реальний push і придатність безкоштовного кандидата; без підтвердження платформи наступна реалізація не починається. Базова валідація даних, доступ до власної історії та ідемпотентність додаються від першої відповідної задачі, а не відкладаються до фінального приймання.

## 01. Пілот: серверна подія → історія без акаунта

Тип: **AFK**. Залежить від: немає. User stories: 21, 22, 32, 34.

Запланований файл: `01-installation-history-pilot.issue.md`.

### Що побудувати

Після першого налаштування інсталяція реєструється без логіна й отримує власну історію. Контрольована публікація валідного графіка проходить через серверне сховище та API до мінімальної картки на вкладці «Сповіщення». Це локально перевірюваний наскрізний пілот, який не потребує хмарних доступів.

### Критерії приймання

- [ ] Інсталяція має стабільний ідентифікатор і секрет доступу; повторна реєстрація не дублює її, чужа історія недоступна.
- [ ] Історія починається з успішного підключення; попередні регіональні події не додаються. Дані події записані до будь-якої спроби доставки.
- [ ] Тестовий сценарій із валідним графіком створює один запис, повертає його через API та показує картку; контрольоване джерело ізольоване від production.
- [ ] Є стани завантаження, порожньої історії й помилки з повтором. Unit, інтеграційна та компонентна перевірки доводять поведінку, включно з повторним отриманням без дублікатів.

## 02. Реальний push і перевірка безкоштовної платформи

Тип: **HITL**. Залежить від: 01. User stories: 2, 17, 18, 19, 20, 22, 26, 37, 38.

Запланований файл: `02-real-push-free-platform-pilot.issue.md`.

### Що побудувати

Публікація з пілота надсилається через Expo на фізичний телефон із закритим застосунком і відкриває свою картку. Пояснення після першого вибору черги керує запитом дозволу. Прототип у Cloudflare вимірює реальний шлях отримання графіка, збереження події та розсилки для 100 тестових інсталяцій.

Участь людини: забезпечити власні Cloudflare/Expo та FCM/APNs доступи, за потреби платформні credentials, і звірити виміряний висновок про безкоштовний кандидат. Код, тести й відтворюваний сценарій готуються до перевірки.

### Критерії приймання

- [ ] Системний дозвіл запитується лише після «Увімкнути сповіщення». Відмова не блокує історію; фактичний стан ОС показано, є перехід до її налаштувань.
- [ ] Налаштовані власний Expo/EAS проєкт і відповідні credentials; доставку та відкриття запису підтверджено на Samsung. У звіті чітко відокремлено неперевірені платформи.
- [ ] Worker фактично отримує й валідно обробляє графік обленерго; перевірено cron, REST-доставку, початковий fan-out на 100 інсталяцій, CPU, підзапити та квоти D1.
- [ ] Є виміряний висновок щодо безкоштовного кандидата. Непроходження обмежень блокує наступні задачі до погодженого перегляду архітектури; платний тариф не вмикається автоматично.

## 03. Щохвилинні публікації графіків на сьогодні й завтра

Тип: **AFK**. Залежить від: 02. User stories: 9, 10, 16, 21, 23, 36.

Запланований файл: `03-schedule-publications.issue.md`.

### Що побудувати

Спільний серверний цикл перевіряє дві дати та повідомляє про першу публікацію нового дня: push для підключених інсталяцій і картка «Опубліковано графік». Збережений базовий стан переживає перезапуск.

### Критерії приймання

- [ ] Датоване джерело опитується раз на 60 секунд для сьогодні й завтра за Europe/Kyiv; кількість запитів не залежить від кількості користувачів.
- [ ] Валідна перша публікація нового дня створює одну подію та історію вже підключених інсталяцій, включно з відсутнім дозволом або токеном.
- [ ] Початковий snapshot уже відомого дня та повторна незмінна відповідь не запускають стару публікацію. Різниця оформлення HTML не створює подію.
- [ ] Порожній HTTP 200, неправильна дата, помилка та невідомий HTML зберігають останній валідний стан; підтверджена відсутність відключень розпізнається окремо. Перевірено весь шлях до push і картки.

## 04. Регіональні зміни графіка: push та історія

Тип: **AFK**. Залежить від: 03. User stories: 10, 11, 14, 16, 21, 36.

Запланований файл: `04-regional-schedule-changes.issue.md`.

### Що побудувати

Зміна змісту графіка створює картку «Графік змінено» та регіональний push незалежно від черги користувача. Виправлення лише минулих годин зберігається в історії без push.

### Критерії приймання

- [ ] Детектор порівнює нормалізований зміст усіх повернутих черг; зміна часу публікації або порядку рядків без зміни станів не створює повідомлення.
- [ ] Поточні/майбутні зміни надсилаються також інсталяції, чергу якої не змінено; лише минулі зміни не надсилаються, але відображаються.
- [ ] Публікація та зміна мають різні типи, заголовки, час події та дату графіка; повторний cron не дублює історію.
- [ ] Інтеграційні й компонентні тести перевіряють сьогодні/завтра, регіональну аудиторію та межу між минулим і майбутнім.

## 05. Незалежний перемикач push про графіки

Тип: **AFK**. Залежить від: 04. User stories: 12, 13.

Запланований файл: `05-regional-push-preference.issue.md`.

### Що побудувати

Користувач вимикає push про публікації та зміни через загальний перемикач, але продовжує бачити обидва типи в історії. Налаштування зберігається на пристрої та сервері.

### Критерії приймання

- [ ] Перемикач увімкнений за замовчуванням; стан переживає перезапуск і передається серверу з версією налаштувань.
- [ ] За вимкнення публікації та зміни продовжують створювати записи, але не створюють push для цієї інсталяції.
- [ ] Перемикач не змінює прапорці локацій; подальше додавання попереджень використовує незалежний стан.
- [ ] Повторна або застаріла синхронізація не повертає старе значення. UI доступний screen reader; серверний і компонентний тести перевіряють історію без push.

## 06. Попередження за 10 хвилин для однієї локації

Тип: **AFK**. Залежить від: 04. User stories: 1, 2, 7, 15, 16, 21, 22, 36.

Запланований файл: `06-ten-minute-location-warning.issue.md`.

### Що побудувати

Для однієї збереженої локації сервер планує попередження про підтверджений стан off, зберігає його в історії та надсилає push за 10 хвилин. Картка містить дату, чергу, локацію й абсолютний час.

### Критерії приймання

- [ ] Контрольований час доводить формування за 10 хвилин, роботу 24/7 і відсутність попереджень для possible, unknown та відновлення.
- [ ] Якщо графік уперше отримано після потрібного моменту, попередження пропущено; подія публікації/зміни залишається. Після простою наздоганяння немає.
- [ ] За збоїв джерела попередження використовує кеш лише за останньої успішної перевірки ≤5 хвилин тому; невдала перевірка не оновлює цей час.
- [ ] Дата/час обчислюються для Києва з переходом через північ і зміною UTC-зсуву; строк push закінчується до початку відключення. Унікальність завдання й актуальна версія перевіряються перед відправленням.
- [ ] Unit та інтеграційні тести покривають часові межі й свіжість; native/компонентна перевірка показує запис незалежно від доставки.

## 07. Попередження для всіх локацій та їхні перемикачі

Тип: **AFK**. Залежить від: 06. User stories: 3, 4, 5, 6, 12, 35.

Запланований файл: `07-all-location-subscriptions.issue.md`.

### Що побудувати

Усі збережені локації мають незалежні попередження; додавання, редагування, вимкнення та видалення синхронізуються з серверним планом. Наявні дані безпечно мігрують.

### Критерії приймання

- [ ] Нова й мігрована локація отримують увімкнений прапорець; назви, черги, іконки та активний вибір збережені.
- [ ] Перемикач локації вимикає тільки її нові попередження; історичні записи залишаються. Загальний перемикач графіків не змінює цієї поведінки.
- [ ] Зміна черги перебудовує її майбутні завдання, видалення скасовує їх після синхронізації; історія зберігає початкові назви/черги.
- [ ] Сценарій із кількома різними чергами перевірено від форми та API до різних push і карток. Версії налаштувань не дозволяють застарілому запиту відновити видалену підписку.

## 08. Одне попередження для локацій спільної черги

Тип: **AFK**. Залежить від: 07. User stories: 7, 8.

Запланований файл: `08-same-queue-warning-grouping.issue.md`.

### Що побудувати

Дві або більше ввімкнених локацій однієї черги й одного відключення отримують один push та один запис із усіма відповідними назвами.

### Критерії приймання

- [ ] Групування виконується в межах інсталяції, черги та відключення; однаковий час різних черг не об’єднує повідомлення.
- [ ] Вимкнені/видалені локації не потрапляють у нове попередження; актуальний перелік перевіряється перед формуванням.
- [ ] Повний перелік доступний у картці; довгі назви переносяться. Push за потреби стисло передає перелік без перевищення розміру payload.
- [ ] Повторні й конкурентні запуски зберігають один логічний запис; тест проходить від підписок до доставки та доступної картки з великим шрифтом.

## 09. Скасування й перенесення попереджень в історії

Тип: **AFK**. Залежить від: 04, 08. User stories: 15, 28, 29, 35.

Запланований файл: `09-warning-rescheduling-and-history.issue.md`.

### Що побудувати

Зміна графіка скасовує застарілі майбутні завдання й оновлює вже сформовану картку позначкою «Скасовано» або «Час змінено». Користувач бачить початковий план, актуальний час та окрему подію зміни.

### Критерії приймання

- [ ] Перед доставкою перевіряються версія графіка й підписка; застаріле завдання не відправляється навіть за конкурентної зміни.
- [ ] Старий запис зберігає початкові дані й отримує актуальну позначку; неоднозначне перенесення не створює вигаданого зіставлення відключень.
- [ ] Нове попередження для перенесеного початку можливе тільки якщо його момент мінус 10 хвилин ще попереду.
- [ ] API повертає оновлення старих записів, а не лише нові ID; клієнт змінює картку без дубліката. Перевірено окремий запис регіональної зміни й серверно-клієнтські перегони.

## 10. Лічильник нових записів і прочитаність

Тип: **AFK**. Залежить від: 04, 06. User stories: 24, 25.

Запланований файл: `10-unread-history-badge.issue.md`.

### Що побудувати

Вкладка «Сповіщення» показує кількість нових записів. Відкриття та завантаження історії позначають відображену межу прочитаною без втрати подій, що надійшли одночасно.

### Критерії приймання

- [ ] Лічильник рахує повідомлення історії незалежно від дозволу ОС або успіху push; системний launcher badge не додається.
- [ ] API й клієнт використовують стабільну межу прочитання; нова подія після цієї межі залишається непрочитаною.
- [ ] Помилка завантаження не обнуляє невідомі записи; оновлення позначки старого запису не створює його копію.
- [ ] Інтеграційні й компонентні тести покривають повторне відкриття, пагінацію та одночасне надходження. Лічильник має доступну назву.

## 11. Офлайн-історія та синхронізація після відновлення зв’язку

Тип: **AFK**. Залежить від: 05, 07, 09, 10. User stories: 23, 30, 31, 35.

Запланований файл: `11-offline-history-and-settings-sync.issue.md`.

### Що побудувати

Без інтернету користувач бачить уже завантажену історію. Повернення зв’язку синхронізує нові події, виправлення, прочитаність та офлайн-зміни підписок.

### Критерії приймання

- [ ] Кешована історія доступна з позначкою «Без інтернету»; незавантажені записи не вважаються доступними. Є перше завантаження, порожній стан, повтор і помилка з кешем.
- [ ] Стабільна пагінація та повторна синхронізація не дублюють записи; старі скасування/перенесення приходять незалежно від курсора нових записів.
- [ ] Офлайн-зміни локацій і перемикачів збережені локально з видимим станом очікування синхронізації; після зв’язку серверний план відповідає останнім налаштуванням.
- [ ] Перевірено перезапуск офлайн, відновлення зв’язку, API-недоступність та незалежність читання історії від доступності обленерго.

## 12. Перехід із push до запису та графіка його дати

Тип: **AFK**. Залежить від: 09, 11. User stories: 26, 27.

Запланований файл: `12-notification-and-dated-schedule-navigation.issue.md`.

### Що побудувати

Холодний або теплий запуск із будь-якого push відкриває та знаходить потрібну картку. Її дія показує графік саме зазначеної дати, включно із завтра, або явну недоступність.

### Критерії приймання

- [ ] Payload має стабільний ID; відкриття завантажує потрібний запис поза першою сторінкою й прокручує до нього без дублювання.
- [ ] Пройдені холодний/теплий запуск, відсутній кеш, повільна мережа й офлайн; користувач бачить явний стан, якщо запис поки недоступний.
- [ ] «Переглянути графік» використовує дату картки, а не сьогодні; недоступний графік має окреме повідомлення без підміни іншою датою.
- [ ] Перевірено всі три типи, картку зі зміненим часом і native-переходи. Повний календар або порівняння версій не додаються.

## 13. 30 днів історії та нова інсталяція

Тип: **AFK**. Залежить від: 11, 12. User stories: 32, 33, 34.

Запланований файл: `13-history-retention-and-reinstallation.issue.md`.

### Що побудувати

Історія автоматично обмежується 30 днями на сервері й пристрої. Перевстановлення створює нову історію; відкриття старого push не веде до помилкової картки.

### Критерії приймання

- [ ] Строк рахується від початкового часу повідомлення; зміна позначки не продовжує його. Прострочений кеш прибирається також офлайн.
- [ ] Очищення виконується обмеженими порціями та прибирає непотрібні пов’язані завдання/версії; перевірено граничний момент 30 днів.
- [ ] Новий ідентифікатор інсталяції не отримує старих подій; заміна токена тієї самої інсталяції зберігає історію.
- [ ] Для видаленого за строком запису з push відкривається історія з поясненням. Немає ручного видалення, акаунта або міжпристроєвого відновлення.

## 14. Відновлення push після помилок і зміни токена

Тип: **AFK**. Залежить від: 06, 09, 11. User stories: 2, 15, 20, 22, 31, 36, 38.

Запланований файл: `14-push-recovery-and-job-idempotency.issue.md`.

### Що побудувати

Зміни дозволу або токена й тимчасові збої доставки не руйнують історію та майбутні повідомлення. Сервер стійко відновлює обробку завдань без дублікатів історії й запізнілих попереджень.

### Критерії приймання

- [ ] Клієнт актуалізує дозвіл і токен після повернення в застосунок; сервер припиняє використання невалідного токена, новий токен не створює другу інсталяцію.
- [ ] Оброблено tickets/receipts, помилки, неоднозначний timeout, конкурентний cron і перезапуск між записом та відправленням; статус провайдера не подається як підтвердження показу ОС.
- [ ] Повтори обмежені строком і актуальністю події. Пропущені попередження не наздоганяються, застарілі версії не відправляються; власна історія не дублюється.
- [ ] Завершений сценарій збою та відновлення перевірено від серверного стану до синхронізованої картки й наступного коректного push. Є вимірювання помилок/затримок без токенів або секретів у журналах.

## 15. Приймання безкоштовного пілота на 100 користувачів

Тип: **HITL**. Залежить від: 13, 14. User stories: 1, 2, 3, 7, 8, 17, 19, 21, 26, 27, 28, 29, 30, 31, 33, 36, 37, 38.

Запланований файл: `15-free-pilot-native-acceptance.issue.md`.

### Що побудувати

Увесь реалізований шлях проходить приймання на фізичних пристроях і в безкоштовному хмарному середовищі. Пілот на 100 інсталяцій перевіряє нагадування, масові зміни, історію, відновлення та очищення з виміряними квотами.

Участь людини: забезпечити пристрої/доступи для платформ випуску, провести потрібне ручне приймання доступності та погодити висновок щодо пілота.

### Критерії приймання

- [ ] Є відтворюваний звіт щодо звичайного циклу, масової зміни, всіх увімкнених локацій, 30-денного обсягу, синхронізації та очищення; CPU, підзапити, D1 і виклики вкладаються в безкоштовні ліміти.
- [ ] Серверне формування та доставка виміряні окремо; документовано допустиме технічне вікно cron без наздоганяння пропущених моментів. Перевірено доступність обленерго з реальної платформи.
- [ ] Пройдені native-сценарії на Android Samsung та на кожній платформі випуску, включно з iOS перед її випуском; неперевірене не позначається завершеним.
- [ ] Картки, перемикачі, лічильник і переходи пройшли вузький екран, шрифт 200%, TalkBack/VoiceOver; type-check, lint та релевантні тести проходять.
- [ ] Результат погоджений як пілот з бюджетом $0. За провалу платформи чи відсутності потрібного пристрою зафіксований конкретний незакритий критерій; платний тариф не вмикається.
